# Этап 5 — безопасная инвентаризация и импорт без дублирования

## Важное решение по защите от дублей

На этом этапе мы **не переносим данные напрямую в рабочие таблицы API**. Сначала формируется проверяемый снимок исходной SQLite-базы в изолированной схеме PostgreSQL `legacy_import`. Это сохраняет все исходные таблицы, пользовательские поля, значения родственников и вложения, не пытаясь угадывать их смысл.

Для каждого логического источника задаётся постоянный `--source-id` (например, `main-kartoteka`). Его нужно повторно использовать для всех резервных копий именно этой базы. В PostgreSQL строка имеет уникальный ключ `(source_id, table_name, row_key)`, где `row_key` строится из первичного ключа исходной таблицы. Поэтому повторный импорт того же снимка пропускается, а обновлённая резервная копия обновляет существующие staging-строки, а не добавляет их повторно.

Если в новой копии строка отсутствует, она не удаляется автоматически: ей ставится `present_in_latest=false`. Это защищает данные от случайной потери. Такие строки нужно изучить при сверке перед окончательным преобразованием.

> Не задавайте разные `--source-id` для разных копий одной и той же базы: это намеренно создаст два независимых набора источников. Не объединяйте разные базы под одним ID, если это не одна логическая картотека.

## 1. Создать резервную копию

1. Закройте старую программу.
2. Скопируйте файл базы `kartoteka.db` в отдельную резервную папку.
3. Не изменяйте и не удаляйте оригинал. Импорт читает только копию в режиме read-only.

## 2. Проверить структуру без персональных данных

```powershell
py -3 migration\inspect_sqlite.py C:\Backup\kartoteka.db --output sqlite_inventory.json
```

Отчёт содержит имена таблиц, колонки, связи, количество строк и SHA-256, но не значения карточек сотрудников.

## 3. Пробный запуск (ничего не записывает в PostgreSQL)

```powershell
py -3 migration\snapshot_to_postgres.py C:\Backup\kartoteka.db --source-id main-kartoteka
```

Проверьте таблицы и количества в выводе. Убедитесь, что `--source-id` — постоянное имя этой логической базы.

## 4. Импорт в staging-схему

Установите зависимость:

```powershell
py -3 -m pip install -r migration\requirements.txt
```

Задайте переменную `KARTOTEKA_DB_CONNECTION` для отдельной целевой базы PostgreSQL, затем выполните:

```powershell
py -3 migration\snapshot_to_postgres.py C:\Backup\kartoteka.db --source-id main-kartoteka --apply
```

Импорт транзакционный: при ошибке вся операция откатывается. Файл проверяется по SHA-256 до и после чтения, чтобы не импортировать изменившуюся во время процесса базу.

## 5. Проверка результата

В PostgreSQL проверьте:

```sql
SELECT * FROM legacy_import.dedup_sources;
SELECT table_name, COUNT(*)
FROM legacy_import.dedup_rows
WHERE source_id = 'main-kartoteka' AND present_in_latest = true
GROUP BY table_name ORDER BY table_name;
SELECT table_name, COUNT(*)
FROM legacy_import.dedup_rows
WHERE source_id = 'main-kartoteka' AND present_in_latest = false
GROUP BY table_name ORDER BY table_name;
```

Число `present_in_latest=true` по каждой таблице должно совпадать с инвентаризацией текущей резервной копии. Повторный запуск на том же файле и с тем же `--source-id` не должен увеличивать количество строк.

## Что этот этап не делает

Это не окончательная миграция в нормализованные таблицы `Employee`, `Relative`, `Award` и другие сущности API. Исходная база хранит часть параметров в динамических таблицах `fields`, `field_values` и `relative_values`; до преобразования нужно сопоставить эти поля новой модели и отдельно сверить вложения. Не запускайте очистку staging-данных и не переключайте пользователей на новую систему до завершения сверки.
