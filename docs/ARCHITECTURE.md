# Архитектура и план перехода

## Целевая схема

```text
Рабочие места в локальной сети
          |
          | HTTPS (браузер)
          v
ASP.NET Core API на выделенном/назначенном рабочем компьютере
          |
          +---- ASP.NET Core Identity + JWT / роли
          |
          +---- PostgreSQL (единый источник данных)
          |
          +---- журнал аудита
```

Старый Tkinter-клиент не должен подключаться к PostgreSQL напрямую: иначе правила доступа можно обойти.
Клиенты работают только через API. Сервер проверяет роль на каждом защищённом endpoint.

## Этапы миграции без потери данных

1. Сохранить неизменяемую резервную копию `kartoteka.db`; вычислить SHA-256 и записать контрольную сумму.
2. Изучить фактическую схему SQLite: таблицы, колонки, связи, вложения и пользовательские поля.
3. Создать PostgreSQL-схему и прогнать EF Core migrations на тестовой БД.
4. Разработать импортёр с режимом `--dry-run`, таблицей сопоставления старых ID новым ID, протоколом ошибок и повторным запуском без дубликатов.
5. Сначала перенести тестовую копию, сравнить количество организаций/подразделений/сотрудников/родственников/вложений.
6. Проверить выборочные карточки и SHA-256 каждого перенесённого файла.
7. Выполнить приёмочные тесты ролей и уведомлений.
8. Только после подписанной сверки переключить пользователей на новый сервер. Старую БД оставить в архиве до окончания периода проверки.

## Модель данных

Сотрудник — центральная сущность. Автомобили, категории ВУ, родственники, должности, классность,
награды, командировки и вложения вынесены в отдельные таблицы, поскольку допускают несколько записей
и/или историю. Это предварительная нормализованная модель: после анализа реальной SQLite-схемы она
должна быть согласована с фактическими полями программы и требованиями заказчика.

## Решения по безопасности

- Не включать пароль в `appsettings.json` для рабочей среды; использовать переменные окружения или Secret Manager.
- Не открывать PostgreSQL на клиентские компьютеры; порт БД доступен только приложению и администраторам БД.
- Ограничить API локальной сетью и настроить HTTPS с доверенным сертификатом.
- Резервные копии шифровать, ограничить круг лиц, проверять восстановление.
- Не писать в аудит полные карточки и содержимое файлов; фиксировать тип действия, объект и исполнителя.
- Для персональных данных определить срок хранения и порядок удаления/архивирования.
