# Этап 22 — серверная модель дополнительных сведений и отпусков

## Что добавлено

- `EmployeeExtendedData`: ИНН, СНИЛС, ПЭК, дактилоскопия и дата, группа крови/резус-фактор, факт и дата ДНК-теста, даты УМО, категория годности, антропометрия, размеры одежды/обуви, реквизиты водительского удостоверения.
- `EmployeeConfidentialHealthRecord`: отдельная сущность для категории годности по психиатрическому освидетельствованию и ограниченной заметки. Её API доступен только роли `admin`; сведения не включаются в обычный DTO сотрудника и список сотрудников.
- `EmployeeLeaveRecord`: плановые и фактические даты, вид, статус, рассчитанные/уточнённые сутки и примечание.
- `EmployeeLeaveEntitlement`: годовые нормы основного, ветеранского и дополнительного отпуска, перенос и корректировка с обязательным основанием. Нормы не зашиты в код: их устанавливает уполномоченный пользователь.
- `EmployeeLeavePreference`: приоритетные месяцы сотрудника.
- `LeaveBlackoutPeriod`: общие запретные даты или даты для подразделения.
- Уведомления о днях рождения за 7 дней и об окончании УМО за один календарный месяц.

## API

- `GET/PUT /api/employees/{id}/extended-data` — расширенные сведения, только `admin` на этом этапе.
- `GET/PUT /api/employees/{id}/confidential-health` — ограниченные психиатрические сведения, только `admin`.
- `GET/POST /api/employees/{id}/leaves` — просмотр/создание отпусков; создание и изменение только `admin`/`editor`.
- `PUT/DELETE /api/employees/{id}/leaves/{leaveId}` — изменение/отмена; запрос всегда проверяет владельца `EmployeeId`.
- `GET/PUT /api/employees/{id}/leave-entitlement?year=YYYY` — просмотр остатка и настройка годовых норм; изменение только `admin`.
- `GET/PUT /api/employees/{id}/leave-preferences?year=YYYY` — приоритетные месяцы сотрудника.
- `GET/POST/DELETE /api/leave-blackouts` — просмотр, добавление и деактивация запретных периодов; изменения только `admin`.
- `GET /api/alerts` — добавлены события дня рождения и окончания УМО.

## Обновление базы

1. Сделать проверенную резервную копию PostgreSQL.
2. На тестовой копии выполнить `scripts/03_stage22_employee_extensions_and_leaves.sql` от имени владельца схемы.
3. Запустить приложение и проверить `/health`, авторизацию, API и аудит.
4. Перед выпуском обновить EF Core migration snapshot и добавить интеграционные тесты против тестовой PostgreSQL. В исходном архиве не было папки `Migrations`, поэтому SQL-патч намеренно отделён и не выдаётся за автоматически сгенерированную EF-миграцию.

## Ограничения этапа

- Это серверный этап: UI для новых полей и отдельное окно отпусков ещё предстоит подключить.
- Автоматическое распределение отпусков и проверка минимальной укомплектованности 30% ещё не реализованы. Текущий этап только хранит исходные данные для следующего планировщика.
- Расчёт «остатка» опирается на введённые нормы и фактически использованные дни. Юридические правила начисления необходимо утвердить отдельно; система не подставляет неподтверждённые нормы.
- Офлайн-режим и синхронизация не реализованы на этом этапе: их нельзя безопасно имитировать только браузерным кэшем.
- В текущей среде отсутствует .NET SDK, поэтому `dotnet build` выполнить не удалось. Статические проверки и `node --check` не заменяют сборку и интеграционные испытания.
