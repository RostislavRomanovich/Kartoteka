# Этап 6. Чистая схема базы данных PostgreSQL

## Назначение

Новая система разворачивается на пустой рабочей базе PostgreSQL. Демонстрационные записи из старой программы не импортируются. Схема формируется миграциями Entity Framework Core из текущих моделей проекта.

## Основные сущности

- `AspNetUsers` и таблицы ASP.NET Identity — учётные записи.
- `Employees` — карточки сотрудников, персональные данные, контракт, допуск, воинский учёт и перевод.
- `OrganizationalUnits` — иерархия подразделений; сотрудник может быть связан с подразделением через `OrganizationalUnitId`.
- `EmployeeCars` — любое количество транспортных средств у сотрудника.
- `DrivingLicenseCategories` — категории водительского удостоверения и даты истечения.
- `Relatives` — родственники, дети, сведения об учёбе и документы.
- `PositionHistories`, `ClassnessHistories` — история должностей и классности.
- `Awards`, `BusinessTrips` — награды и командировки.
- `EmployeeMessengers` — несколько контактов в мессенджерах.
- `PersonalFeatures` — особые приметы: татуировки, шрамы, родинки и другие признаки. Фото связывается с записью через `AttachmentId` и хранится во вложениях; доступ к фото должен проверяться отдельной авторизацией.
- `CustomFieldDefinitions`, `EmployeeCustomFieldValues`, `RelativeCustomFieldValues` — дополнительные поля, настраиваемые администратором.
- `EmployeeAttachments` — файлы, связанные с карточкой сотрудника.
- `AuditLogs` — журнал событий.

## Ограничения против дублирования

1. У сотрудника есть внутренний первичный ключ `Id`.
2. Номер личного дела/табельный номер уникален, если он заполнен. Номер должен нормализоваться на уровне приложения перед сохранением.
3. Индекс по ФИО предназначен для поиска и намеренно не уникален: у разных людей могут совпадать ФИО.
4. Для сотрудника нельзя создать две одинаковые категории водительских прав.
5. Нельзя создать повторный контакт с тем же названием мессенджера и контактом в одной карточке.
6. Для одного сотрудника и одного определения дополнительного поля допускается только одно значение.
7. В одной родственной карточке для одного определения дополнительного поля допускается только одно значение.
8. Период должности и командировки проверяется ограничением БД: дата окончания не может быть раньше даты начала.
9. Срок контракта в месяцах должен быть положительным.

## Удаление и история

- Связанные сведения каскадно удаляются только при физическом удалении сотрудника; рабочий интерфейс должен по умолчанию архивировать карточку, а не удалять её.
- Подразделение нельзя удалить, пока у него есть дочерние подразделения. Сотрудник при удалении подразделения не должен исчезать; связь настроена на `SET NULL`.
- Определения дополнительных полей нельзя удалить, пока существуют значения; вместо удаления следует выключать `IsActive`.
- Удаление учётных записей, просмотр файлов и изменение чувствительных данных должны отдельно журналироваться.

## Важные границы этапа

Это схема данных и ограничения, а не утверждение о готовом интерфейсе всех перечисленных функций. Для полноценного использования нужны API/формы и отдельные проверки прав на каждую операцию. Значения в таблицах не заменяют правовую проверку правил расчёта выслуги или сроков уведомлений.

## Применение миграций

Сценарий `scripts/windows/Prepare-Local.ps1`:

- если миграций ещё нет — создаёт `InitialCreate` из текущей модели;
- если предыдущая миграция уже есть — создаёт `Stage6CoreSchema` для новых сущностей и ограничений, если такая миграция ещё не создана;
- применяет миграции к указанной базе.

Перед запуском на существующей базе обязательно сделать резервную копию. Не использовать демонстрационные данные как рабочие.
